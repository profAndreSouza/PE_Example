PE_Example · apresentação técnica

Fluxo de trabalho das equipes Backend, Quality e DevOps

Passo a passo da implementação da API, da definição dos contratos até a validação integrada. Backend e Quality desenvolvem em paralelo; DevOps automatiza os testes em pipelines.

Backend

Java 21, Spring Boot 3, Spring Data JPA e PostgreSQL.

Quality

Especifica e implementa testes unitários, de controller, API e E2E.

DevOps

Configura e mantém as pipelines que compilam e executam as suítes.

Escopo funcional: CRUD de usuários e CRUD de projetos de extensão.

01 · Objetivo e escopo

O produto e o fluxo que serão explicados

Usuário

Cadastro, consulta, atualização e remoção. Campos: nome, e-mail, tipo e status.

ALUNO, PROFESSOR, ADMINISTRADOR; ATIVO, INATIVO.

Projeto de extensão

Cadastro, consulta, atualização e remoção. Cada projeto referencia um usuário coordenador.

EM_ANALISE, EM_ANDAMENTO, CONCLUIDO.

Regra de integração: não se testa apenas se a tela ou a API existe. É preciso validar que os dados atravessam as camadas e preservam as regras do domínio.

02 · Responsabilidades

As equipes têm objetivos diferentes e complementares

Equipe Backend

  • Implementar os endpoints e o contrato JSON.
  • Validar entrada e regras de negócio.
  • Persistir dados e relações no PostgreSQL.
  • Entregar respostas e erros consistentes.
  • Fornecer regras, contratos e código testável; apoiar Quality na análise de falhas.

Equipe Quality

  • Transformar requisitos em cenários verificáveis.
  • Implementar testes unitários, de controller, API e E2E.
  • Testar o serviço HTTP real e os dados persistidos.
  • Verificar fluxos completos no navegador.
  • Reproduzir falhas com entradas e resultados esperados.
  • Registrar evidências e tornar a execução repetível.

Equipe DevOps

  • Criar e manter workflows no GitHub Actions.
  • Configurar versões, dependências, cache e serviços de CI.
  • Executar as suítes Java, frontend, API e E2E.
  • Publicar resultados e evidências das execuções.

03 · Trabalho paralelo

O paralelismo começa pelo contrato

1. AlinharRequisitos, payloads, regras e códigos HTTP.
→
2. DividirBackend implementa; Quality escreve testes; DevOps configura a execução automatizada.
→
3. IntegrarExecutar os testes contra a implementação real.
→
4. CorrigirReproduzir falhas e reexecutar os mesmos casos.

Backend não precisa esperar

Define DTOs, regras e assinaturas. Compartilha exemplos e ajusta o código para que possa ser testado.

Quality não precisa esperar

Escreve testes Java com base nas regras e prepara os testes de API/E2E com base no contrato.

DevOps também começa cedo: configura os workflows enquanto Backend e Quality implementam código e testes. O ponto de sincronização é o contrato, não uma entrega em cascata.

06 · Modelagem

As entidades refletem o modelo relacional

Usuario

Entidade JPA mapeada para tb_usuario.

Possui ID, nome, e-mail único, tipo, status e data de criação.

ProjetoExtensao

Entidade JPA mapeada para tb_projeto_extensao.

Contém título, descrição, status, datas e referência obrigatória ao coordenador.

@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "coordenador_id", nullable = false)
private Usuario coordenador;

Relação: um usuário pode coordenar vários projetos; cada projeto tem um coordenador.

07 · DTO e validação

O DTO protege a fronteira da API

O cliente envia um objeto de entrada. A entidade não é exposta diretamente como contrato HTTP.

public class UsuarioCreateDTO {
  @NotBlank
  @Size(max = 100)
  private String nome;

  @NotBlank
  @Email
  @Size(max = 150)
  private String email;

  @NotNull
  private TipoUsuario tipo;

  private StatusUsuario status;
}

Quando falha

@Valid interrompe o processamento antes do Service e o handler global devolve 400.

Quando passa

O Service aplica as regras do domínio e transforma o resultado em DTO de resposta.

08 · Controller

O controller traduz HTTP em chamada de caso de uso

@PostMapping
public ResponseEntity<UsuarioDTO> criar(
    @Valid @RequestBody UsuarioCreateDTO dto) {
  UsuarioDTO criado = usuarioService.criar(dto);
  return ResponseEntity.status(HttpStatus.CREATED).body(criado);
}

Recebe

JSON e parâmetros da rota.

Delega

Chama o Service; não contém regra de negócio.

Responde

DTO e código HTTP coerente com a operação.

Arquivos: UsuarioController.java e ProjetoExtensaoController.java.

09 · Leitura, busca e paginação

As listagens limitam volume e permitem pesquisa

GET /api/usuarios?page=0&size=10&busca=ana
GET /api/projetos-extensao?page=0&size=10&busca=inclusao
  1. Controller recebe busca e Pageable.
  2. Sem termo, Service pede uma página ordenada ao Repository.
  3. Com termo, Repository procura em nome/e-mail ou título/descrição, sem diferenciar maiúsculas.
  4. Service transforma cada entidade em DTO preservando os metadados da página.
{
  "content": [],
  "totalElements": 0,
  "totalPages": 0,
  "number": 0,
  "size": 10
}

O backend limita o tamanho máximo de página a 100 registros.

10 · Caso de uso: usuário

Cadastro de usuário — sequência interna

  1. Controller recebe UsuarioCreateDTO e executa validações declarativas.
  2. Service consulta se o e-mail já existe.
  3. Se existir, lança BusinessException; nenhum registro é salvo.
  4. Se não existir, constrói a entidade e define ATIVO quando o status não foi informado.
  5. Repository persiste a entidade e o Service devolve UsuarioDTO.
  6. Controller responde 201 Created.
if (usuarioRepository.existsByEmail(dto.getEmail())) {
  throw new BusinessException("Já existe um usuário cadastrado...");
}

Quality testa os dois caminhos: e-mail novo retorna 201; e-mail repetido retorna 400.

11 · Caso de uso: projeto

Cadastro de projeto — validar relações e datas

  1. Validar campos obrigatórios do DTO.
  2. Buscar o usuário informado em coordenadorId.
  3. Se não existir, lançar ResourceNotFoundException e responder 404.
  4. Se estiver inativo, lançar BusinessException e responder 400.
  5. Se a data final anteceder a inicial, rejeitar o cadastro.
  6. Persistir projeto e devolver DTO com ID e nome do coordenador.
if (coordenador.getStatus() == StatusUsuario.INATIVO)
  throw new BusinessException("O coordenador selecionado está INATIVO.");

if (dto.getDataFim() != null
    && dto.getDataFim().isBefore(dto.getDataInicio()))
  throw new BusinessException("A data fim não pode ser anterior à data de início.");

12 · Atualização e remoção

As operações de escrita usam a mesma separação de camadas

PUT

  1. Localizar o registro pelo ID.
  2. Retornar 404 se não existir.
  3. Revalidar e-mail ou coordenador e regras de negócio.
  4. Atualizar campos, persistir e responder 200 com DTO.

DELETE

  1. Localizar o registro pelo ID.
  2. Retornar 404 se não existir.
  3. Solicitar remoção ao Repository.
  4. Responder 204 sem corpo.

A chave estrangeira restringe a exclusão de usuário que ainda coordena projetos.

14 · Testes unitários · responsabilidade de Quality

Quality implementa testes unitários para as regras do backend

@Test
void lancarExcecaoCoordenadorInativo() {
  coordenador.setStatus(StatusUsuario.INATIVO);
  when(usuarioRepository.findById(1L))
      .thenReturn(Optional.of(coordenador));

  assertThrows(BusinessException.class,
      () -> projetoExtensaoService.criar(createDTO));

  verify(projetoExtensaoRepository, never())
      .save(any(ProjetoExtensao.class));
}

Preparar

Criar DTO e entidades para um cenário conhecido.

Executar

Chamar diretamente o método do Service.

Verificar

Exceção esperada e ausência de persistência.

Responsabilidade de Quality

Definir o cenário, a asserção e as interações esperadas; manter os testes JUnit/Mockito.

Colaboração de Backend

Explicar as regras e ajustar o código de produção quando necessário para facilitar testes confiáveis.

Os arquivos ficam em backend/src/test/java/.../service/ porque Maven/Spring Boot descobrem e executam os testes Java nesse source set. O diretório não determina a equipe autora.

15 · Testes de controller · responsabilidade de Quality

Quality verifica o contrato MVC com MockMvc

@WebMvcTest(UsuarioController.class)
class UsuarioControllerTest {
  @Autowired MockMvc mockMvc;
  @MockBean UsuarioService usuarioService;

  @Test
  void rejeitaUsuarioSemCamposObrigatorios() throws Exception {
    mockMvc.perform(post("/api/usuarios")
        .contentType(APPLICATION_JSON)
        .content("{\"email\":\"invalido\"}"))
      .andExpect(status().isBadRequest())
      .andExpect(jsonPath("$.fields").exists());
  }
}

MockMvc exercita roteamento e validação do Spring MVC. Quality mantém o teste; Backend apoia no entendimento dos endpoints. O Service é simulado: esse teste não comprova persistência, rede ou integração com PostgreSQL.

16 · Automação · responsabilidade de DevOps

DevOps configura a pipeline que executa os testes

# Na raiz do repositório
docker compose --profile tests run --rm backend-tests

# Alternativa com Maven/JDK instalados em backend/
mvn clean verify
  1. DevOps define o gatilho: push ou pull request que altera o backend.
  2. A pipeline prepara JDK 21 e cache Maven no runner.
  3. Maven compila o código; JUnit executa os testes implementados por Quality.
  4. O workflow publica sucesso ou falha; a proteção de branch do GitHub determina se a aprovação é obrigatória para merge.
  5. Quality analisa a falha do teste; Backend corrige a implementação quando a causa está na regra/código.

O arquivo .github/workflows/backend-ci.yml é uma pipeline de responsabilidade DevOps. Ele executa mvn --batch-mode clean verify; não define a autoria dos testes.

17 · Papel de Quality

Quality verifica o comportamento observável do produto

Testes HTTP

Chamam a API real e verificam status, JSON, persistência e regras.

Testes E2E

Operam a interface real e atravessam frontend, backend e banco.

Evidências

Comando executado, versão, resultado, logs e dados usados.

Distinção entre as suítes

Testes Java mantidos por Quality

Ficam em backend/src/test por convenção de build; verificam regras Java e contrato MVC isoladamente.

Quality: API e E2E

Ficam em quality/tests; detectam incompatibilidades entre serviços, configuração, banco e interface.

Autoria do teste (Quality), localização técnica (source set Java ou pasta quality) e execução automática (DevOps) são responsabilidades distintas.

18 · Preparação de Quality

Preparar os cenários enquanto o backend é implementado

  1. Separar requisitos por recurso: usuário e projeto.
  2. Escrever pré-condição, chamada, entrada, resultado esperado e limpeza.
  3. Definir dados próprios por execução, por exemplo e-mail com timestamp.
  4. Planejar cenários positivos e negativos antes de executar contra o serviço.
  5. Usar o mesmo contrato acordado com Backend: nomes, status e formato de resposta.

Cadastro positivo

Usuário válido deve retornar 201 e ID. Projeto válido deve referenciar o coordenador enviado.

Cadastro negativo

Dados obrigatórios ausentes: 400. Coordenador inexistente: 404. E-mail repetido: 400.

19 · Testes de API

Um teste HTTP executa uma sequência controlada

  1. Aguardar a API ficar disponível.
  2. Consultar uma página e validar content, size e status.
  3. Enviar entrada inválida e verificar 400.
  4. Criar usuário com e-mail exclusivo e guardar o ID retornado.
  5. Repetir o e-mail para provar a regra de unicidade.
  6. Criar projeto associado ao usuário e validar o relacionamento.
  7. Enviar coordenador inexistente e datas inválidas; validar 404 e 400.
  8. Remover os registros criados no bloco finally.

Implementação: quality/tests/api/api.test.js, usando node:test e fetch.

20 · Testes E2E

A jornada E2E começa na interface e termina no banco

1. NavegadorAbrir frontend servido pelo Nginx.
→
2. UsuárioAbrir modal, preencher nome/e-mail e submeter.
→
3. API e bancoConfirmar cadastro e recuperar ID via API.
→
4. ProjetoAbrir tela, selecionar o usuário e enviar o formulário.
→
5. ConferirValidar coordenador na API e mensagem na tela.

O teste exclui projeto e usuário no finally. Isso reduz resíduos e permite repetir a jornada.

Implementação: quality/tests/e2e/extension-project.spec.ts.

24 · Tratamento de falhas

Como diagnosticar uma falha sem misturar camadas

  1. Teste Java falhou: conferir arrange/act/assert, mocks e regra do Service.
  2. Controller falhou: conferir rota, validação, conversão JSON e status.
  3. Teste API falhou: conferir containers, logs do backend, schema e dados de entrada.
  4. Teste E2E falhou: conferir seletor, estado da tela, proxy Nginx e resposta HTTP.
  5. Falha de integração: comparar contrato documentado com request/response reais.
  6. Registrar passos e evidência antes de alterar o teste para fazê-lo passar.
docker compose ps
docker compose logs --tail 100 backend postgres frontend

25 · Critério de pronto

Definição de concluído para Backend, Quality e DevOps

Backend pronto quando

  • Contrato, regras e validação estão implementados.
  • Aplicação sobe no Compose e conversa com PostgreSQL.
  • Colaborou na análise das falhas reportadas pelos testes.
  • Build do backend passa na pipeline.

Quality pronto quando

  • Cenários refletem requisitos e contrato vigente.
  • Testes unitários e de controller estão implementados.
  • API cobre sucesso e erros prioritários.
  • Jornada E2E confirma associação usuário–projeto.
  • Dados de teste são removidos e execução é reproduzível.

DevOps pronto quando

  • Workflows cobrem backend, frontend, Quality e infraestrutura.
  • Comandos e versões estão configurados.
  • Jobs executam em push/PR relevante e mostram resultados.
  • Falhas ficam visíveis para as equipes responsáveis.

26 · Sequência recomendada

Passo a passo operacional da integração

  1. Revisar requisito e DDL; confirmar nomes e cardinalidade.
  2. Publicar contrato do endpoint: URL, request, response e falhas.
  3. Quality escreve o teste unitário da regra; Backend implementa o Service e colabora na testabilidade.
  4. Backend cria controller, validação e mapeamento de resposta.
  5. Quality prepara teste HTTP com dados exclusivos e limpeza.
  6. Quality prepara jornada UI com seletores estáveis e verificação via API.
  7. DevOps cria workflows: Maven/JUnit, lint/build, API/E2E e Terraform.
  8. Executar as pipelines a cada push/PR relevante.
  9. Corrigir divergências na camada responsável e repetir a pipeline de regressão.
  10. Entregar alterações com resultados de CI e evidências.
